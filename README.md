# Sentinel Detection as Code

A detection engineering pipeline for Microsoft Sentinel, built with GitHub and GitHub Actions. Analysts write each rule as YAML. On every pull request the pipeline validates the rule, checks the KQL against the table schemas and generates the deployable Bicep. After review and merge, the native Sentinel Repositories connector deploys the rule to the workspace. Two GitHub agents help with the text work: the ADS document of a rule and the first draft of a new rule.

The focus is what surrounds the deploy step. Deploying a rule is the easy part. The engineering work is in what protects the rule before it reaches the workspace.

Write up of the whole build: [Medium post](https://medium.com/@kelvinzdk/automating-detection-engineering-with-detection-as-code-and-github-actions-for-microsoft-sentinel-b69f0621df7e?postPublishedType=initial)

## How it works

```
Analyst writes Rules/<slug>.yml
        |
        v
Pull request
        |
        v
Rule schema validation   YAML against the JSON Schema, unique rule ids
        |
        v
KQL validation           query against the table schemas, entity columns against the query output
        |
        v
Generate Bicep           CI commits Detections/<slug>.bicep to the PR branch
        |
        v
Human review and merge
        |
        v
Sentinel Repositories deploys Detections/
```

Two principles shape the design:

1. Agents never merge and never deploy. They open a pull request, and a human decides.
2. Anything pasted into an issue is untrusted input. Agents work with minimal tools and have no access to deployment credentials.

## Repository layout

```
.github/
  agents/                    custom agents (ads_writer, detection_drafter)
  ISSUE_TEMPLATE/            ADS request and Detection request forms
  workflows/
    validate_rule_schema.yml schema, KQL and Bicep jobs
    ads_check.yml            ADS presence and structure check
    sentinel_deploy_*.yml    generated by Sentinel Repositories
  copilot-instructions.md    general instructions for Copilot

Rules/                       SOURCE OF TRUTH, one YAML per rule, edit here
Detections/                  GENERATED Bicep, do not edit
Docs/ADS/                    one ADS document per rule
Schemas/                     rule JSON Schema and one file per Sentinel table
Templates/                   ADS template
Tools/                       Bicep generator, validators and the schema downloader
```

Each rule uses the same slug everywhere: `Rules/<slug>.yml`, `Detections/<slug>.bicep` and `Docs/ADS/<slug>.md`.

`Detections/` contains only what is deployed. The Sentinel deploy workflow is scoped to that folder, so schemas, documentation and tooling never reach the deploy step.

## Why YAML as the source and Bicep as the output

Sentinel Repositories deploys ARM and Bicep, not YAML. YAML is easier to review in a diff and easier to write correctly, and it carries metadata that has no place in an ARM resource. A Python script turns the YAML into Bicep, and CI commits the result to the pull request branch, so the reviewer sees exactly what will be deployed. A hand edit to a Bicep file is overwritten on the next run, because the YAML is the source of truth.

## Rule format

One rule is one file. A shortened example:

```yaml
id: d3c1a7f2-6b4e-4c8a-9e51-2f7a0b8c4d16
display_name: "Azure role assignment created"
description: "..."
severity: "Medium"
enabled: true
query: |
  AzureActivity
  | where OperationNameValue =~ "MICROSOFT.AUTHORIZATION/ROLEASSIGNMENTS/WRITE"
  | where ActivityStatusValue =~ "Success"
query_frequency: "PT15M"
query_period: "PT1H"
trigger_operator: "GreaterThan"
trigger_threshold: 0
suppression_enabled: false
mitre_mapping:
  - tactic: "Persistence"
    techniques: ["T1098"]
  - tactic: "PrivilegeEscalation"
    techniques: ["T1098"]
```

The full rule also has entity mappings and incident settings. The JSON Schema uses `additionalProperties: false`, so a typo in a property name fails the pull request.

## Validation

Runs on every pull request. The first two job names are required status checks on the ruleset for `main`.

* **Rule schema validation.** Every YAML against the JSON Schema, and no duplicate rule ids.
* **KQL validation.** Every query is parsed with Microsoft's `@kusto/language-service-next` package, pinned to one version, and resolved against the table schemas in `Schemas/`. A second step checks that every entity mapping points to a column the query returns.
* **Generate Bicep.** Builds the `.bicep` files and commits them to the pull request branch, only when something changed. It uses a fine grained token (`BICEP_BOT_TOKEN`), because a push with the default `GITHUB_TOKEN` does not trigger other workflows.
* **ADS check.** A new rule needs its ADS document, and every ADS file must contain all the template sections with balanced markers.

The table schemas are downloaded with a PowerShell script, only for the tables the rules use. A new table needs one admin run of the script and a committed schema file.

## ADS documentation

Every rule has a document based on the [Palantir Alerting and Detection Strategy framework](https://github.com/palantir/alerting-detection-strategy-framework): Goal, Categorization, Strategy Abstract, Technical Context, Blind Spots and Assumptions, False Positives, Validation, Priority, Response and Additional Resources.

HTML comments mark who owns each section:

| Marker | Written by | What the agent does |
| --- | --- | --- |
| `ads:fixed` | The rule YAML | Copies the values and refreshes them when the rule changes |
| `ads:draft` | The agent | Rewrites it on every request |
| `ads:analyst` | The analyst | Never touches it |

An analyst who edits a draft changes its marker to `ads:analyst`, and from then on the text is theirs.

## Agents

Two custom agents live in `.github/agents/`. They are started by assigning an issue to Copilot and picking the agent in the assign dialog.

| Agent | Input | Output |
| --- | --- | --- |
| `ads_writer` | ADS request issue | `Docs/ADS/<rule>.md` |
| `detection_drafter` | Detection request issue | One new rule in `Rules/`, disabled |

Both open a pull request that goes through the same checks and the same review as any other change. The detection agent prefers behavior over indicators, and it does not write a rule when the table has no schema in the repo. The scope of each agent is written in its instructions, not enforced, so a person reviews every diff.

## Rule lifecycle and conventions

* Never reuse the id of a deleted rule.
* Disable a rule first (`enabled: false`), and only then remove it.
* One rule per file. The file name is the slug.
* Removing a rule takes two steps: delete the YAML and the Bicep in a pull request, then delete the rule in the Sentinel portal.

## Branches, commits and pull requests

Branch names use a prefix, a slash and a short lowercase description with underscores.

| Prefix | Use | Example |
| --- | --- | --- |
| `rule/` | A new rule or a change to a rule | `rule/php2shell_ads` |
| `feat/` | A new capability of the pipeline or the tooling | `feat/column_validator` |
| `fix/` | A fix to the pipeline or the tooling | `fix/detection_template` |
| `docs/` | Documentation only | `docs/readme_update` |
| `chore/` | Maintenance that changes no behavior | `chore/remove_lifecycle` |
| `test/` | A deliberate failure to prove a check works | `test/kql_query_error` |
| `copilot/` | Created by the Copilot cloud agent, not renamed | `copilot/detection-php2shell-exploit` |

Commit messages follow the same prefixes: `feat:`, `fix:`, `docs:`, `chore:` and `test:`. The Bicep bot uses `chore: generate Bicep from rules`.

Every change goes through a pull request. Keep it small, with a title that says what changed, and link the issue when there is one. Merged branches are deleted automatically, and the pull request keeps the history.

## Known limitations

Sentinel Repositories:

* Deleting a file does not delete the rule from the workspace.
* There is no native drift detection. A change made in the portal is only overwritten when the file changes.
* Every JSON file in the scanned path is treated as an ARM template, so the deploy workflow is scoped to `Detections/`.
* The Bicep resource type that works is the legacy `Microsoft.OperationalInsights/workspaces/providers/alertRules`. The newer `Microsoft.SecurityInsights/alertRules` ran green and deployed nothing.

This project:

* The checks prove a query is valid, not that it detects anything.
* Only tables with a committed schema are validated.
* The bot commit works for branches in the same repo, not for forks.
