# Sentinel Detection as Code
 
A detection engineering pipeline for Microsoft Sentinel, built with GitHub and GitHub Actions. Analysts write each rule as YAML. On every pull request the pipeline generates the deployable Bicep, runs validations and tests, and an AI agent drafts the rule documentation using the Palantir Alerting and Detection Strategy (ADS) framework. After review and merge, the native Sentinel Repositories connection deploys the rule to the workspace.
 
The focus is what surrounds the deploy step. Deploying a rule is the easy part. The engineering work is in what protects the rule before and after it reaches the workspace.
 
## How it works
 
```
Analyst writes rules/<slug>.yml and tests
        |
        v
Pull request
        |
        v
CI generates the Bicep from the YAML
AI agent drafts the ADS document for the rule
        |
        v
Validation gate: schema, MITRE, KQL, behavior tests, ADS check
        |
        v
Human review and merge
        |
        v
Sentinel Repositories deploys Detections/
        |
        v
Post deploy check confirms the rule exists in the workspace
```
 
Issues are an optional way in. An analyst can paste a news article or threat report into an issue, and an agent proposes a starting rule and opens a draft pull request. From that point it follows the same path as any other rule.
 
Two principles shape the design:
 
1. The agent never merges and never deploys. It proposes, and a human decides.
2. Anything pasted into an issue or a pull request is untrusted input. Agent steps run with minimal permissions and without access to deployment credentials.
## Repository layout
 
```
.github/
  ISSUE_TEMPLATE/new_detection.yml   optional intake form
  CODEOWNERS
  workflows/
    pr_validate.yml                  generation, ADS agent and validation gate
    issue_to_pr.yml                  optional intake agent
    post_deploy_check.yml            verifies the rule exists after deploy
    sentinel_deploy_*.yml            generated by Sentinel Repositories
.sentinel/                           Repositories tracking data
sentinel-deployment.config
 
rules/                               SOURCE OF TRUTH, edit here
Detections/                          GENERATED Bicep, do not edit
docs/ads/                            one ADS document per rule
tests/<rule_slug>/                   fixtures and expected results
 
templates/                           rule and ADS templates
schemas/                             rule schema, ADS sections, table schema, MITRE lock
tools/                               generator and validators
agent/                               prompts and runners for the agents
```
 
Each rule uses the same slug everywhere: `rules/<slug>.yml`, `Detections/<slug>.bicep`, `docs/ads/<slug>.md` and `tests/<slug>/`. The pipeline fails if one of them is missing.
 
`Detections/` contains only what is deployed. The Sentinel deploy workflow is restricted to that folder, so tests, documentation and tooling never reach the deploy step.
 
## Why YAML as the source and Bicep as the output
 
Sentinel Repositories deploys ARM and Bicep, not YAML. YAML is easier to review in a diff and easier for people and agents to write correctly, and it carries project metadata that has no place in an ARM resource. A generator turns the YAML into Bicep, and the generated file is committed with the rule so the reviewer sees exactly what will be deployed. The pipeline regenerates it and fails if the committed file differs, which prevents hand edits to generated output.
 
## Rule format
 
```yaml
id: <GUID, fixed forever>
name: role_assignment_created        # same as the file name
displayName: Azure role assignment created
description: ...
version: 1.0.0                       # must increase when the rule changes
status: experimental                 # experimental, test, stable, deprecated
severity: Medium
kind: Scheduled
 
attack:
  matrix: enterprise
  tactics: [Persistence, PrivilegeEscalation]
  techniques: [T1098.003]
 
dataSources:
  - table: AzureActivity
    connector: AzureActivity
 
queryFrequency: PT15M
queryPeriod: PT1H
triggerOperator: GreaterThan
triggerThreshold: 0
suppression: { enabled: false, duration: PT1H }
incident:
  create: true
  grouping: { enabled: true, matchBy: [Account] }
eventGrouping: AlertPerResult
query: |
  ...
entityMappings:
  - entity: Account
    fields: { FullName: Caller }
  - entity: IP
    fields: { Address: CallerIpAddress }
customDetails: { ResourceGroup: ResourceGroup }
ads: docs/ads/role_assignment_created.md
tests: tests/role_assignment_created/
owner: <github user>
references: []
```
 
## Validation
 
Runs on every pull request.
 
* **Hygiene.** Schema validation, unique rule id, version bump when the rule changes, slug matches file name.
* **MITRE ATT&CK.** Technique exists in a pinned version of the official data, is not revoked or deprecated, is compatible with the declared tactic, and matches the ADS categorization.
* **KQL.** Static checks against the real table and column list of the workspace. Every column used in `entityMappings` and `customDetails` must be projected by the query.
* **Behavior tests.** Fixtures run against a local Kusto engine. Timestamps are relative because rules use `ago()`.
* **ADS.** All nine sections present, no placeholder text, and consistent with the rule.
* **Generated output.** Bicep is regenerated, compared with the committed file and compiled with `bicep build`.
After the merge, a post deploy check queries the workspace and fails if an expected rule is missing. A green deploy workflow does not prove the rule is deployed. On the first attempt in this project the workflow passed while the rule was skipped, and the only signal was a warning in the log.
 
## ADS documentation
 
Every rule has a document based on the [Palantir Alerting and Detection Strategy framework](https://github.com/palantir/alerting-detection-strategy-framework): Goal, Categorization, Strategy Abstract, Technical Context, Blind Spots and Assumptions, False Positives, Validation, Priority and Response.
 
The agent reads the rule and its tests and drafts the document. A human reviews it. The automated check enforces that every section exists and is filled in, and that the categorization matches the rule. It cannot judge whether the content is correct, which is why review stays with a person.
 
## Rule lifecycle and conventions
 
* Never reuse a rule id. A deleted rule id cannot be reused for some time.
* Retire a rule by setting `enabled` to false first, and only then remove it.
* Bump `version` on every logic change.
* One rule per file. The file name is the slug.
## Known limitations of Sentinel Repositories
 
* Deleting a file does not delete the rule from the workspace.
* There is no native drift detection. A change made in the portal is only overwritten when the file changes.
* Limits apply per workspace and per resource group, so check the current documentation before scaling.
* The deploy script ignores resource types it does not recognize, and a workflow can finish green without deploying anything. The Bicep resource type that works is the legacy `Microsoft.OperationalInsights/workspaces/providers/alertRules`. The newer extension resource type is skipped.
A prune and drift job closes the first two gaps.
 
## Infrastructure
 
The base infrastructure (resource group, workspace, Sentinel onboarding, resource providers and the activity log diagnostic setting) is intended to be managed with Terraform, with the existing resources imported.
